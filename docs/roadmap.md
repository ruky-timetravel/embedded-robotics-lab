# 嵌入式与机器人：Linux 起步的 16 周学习路线

整理日期：2026-10-19。依据用户提供的《嵌入式与机器人：16 周学习路线及项目清单》整理，保留电脑起步、三个项目、验收标准与资料，并将 Linux 提前至第 1 天。

这份文件描述学习计划。已报告的环境和实际完成情况记在 [progress.md](progress.md)；计划中的程序、测试、图表和项目均需以后实际完成。

## 1. 当前起点与学习方式

- 现阶段只有电脑，没有开发板、传感器或底盘，先完成软件与仿真项目。
- 用户已报告 Ubuntu 26.04.1 LTS、x86_64，使用 VMware 虚拟机；Git 2.53、Python 3.14.4、VS Code 1.142。
- C 编译、GDB 断点调试以及第一课程序的验收尚待用户反馈。安装了编辑器不等于已经具有可用的 C 编译与调试环境。
- 全程优先使用现有 Ubuntu 环境。第一阶段不必重装系统，也不必先购买硬件。
- 每周原计划约 10–15 小时；若同时考研，可先保留每周 6–8 小时并延长周期。16 周是弹性排期，验收未通过就继续练习。
- 每课采用“说明概念 → 自己运行 → 观察或修改 → 解释结果 → 留下证据”的顺序。遇到错误先保留完整输出，再定位原因。

学习主线：

**Linux 基础与 C 编译调试 → C 数据结构与状态模块 → PC 协议项目 → FreeRTOS Linux/POSIX 示例 → 电机控制仿真 → C++ 与工程化 → 双轮二维仿真 → ROS 2 与导航仿真。**

从第一天使用 Linux 不代表立即学习内核、驱动或复杂系统管理。先掌握目录、文件、终端、编译和调试所需操作即可。

## 4. 项目 1：PC 设备通信协议与故障测试系统

**优先级：第一必做项目。** 练习 C 模块化、内存边界、流式解析、状态机与测试。

### 4.1 最小版本

1. 用 C 定义帧头、命令、长度、序号、负载和校验。
2. 输入字节数组或测试文件，解析命令与数据。
3. 用函数产生虚拟温度或虚拟轮速。
4. 通过命令修改虚拟设备状态、采样间隔，并读取状态。
5. 分开接收、解析、业务处理和输出模块。

先使用函数调用和文件输入。虚拟串口、复杂图形界面按需求后移。

### 4.2 增强版本

- C 程序作为设备端，Python 作为测试端或上位机。
- 先文件回放，再用本机 TCP 传输字节，练习分段、断线与恢复。
- 传输接口单独封装，便于以后换成 UART。
- 支持开始、停止、状态读取、参数修改、错误应答和日志。
- Python 批量发送测试数据，保存 CSV 并绘图。

本机 TCP 的结果只能说明本机字节流与协议行为。真实 UART 电气接口、串口时序和 MCU 延迟需要设备验证。测 PC 通信时间时优先测请求—应答 RTT，注明测试条件和统计方法。

### 4.3 验收清单

- [ ] 正常帧解析正确，响应命令与序号对应。
- [ ] 一帧逐字节输入、分段输入、一次输入多帧均可处理。
- [ ] 帧头前有杂字节时能恢复同步。
- [ ] 坏校验、异常长度、半帧、空负载和最大负载有明确处理。
- [ ] 环形缓冲区满时有明确策略与错误计数。
- [ ] 连续运行至少 1000 个自动化命令用例，保留输入、实际结果与原始日志。
- [ ] 故障后仍能解析后续合法帧；检查越界、卡住及资源使用问题。
- [ ] 记录协议版本、构建方式、复现步骤和已知问题。

计划交付：C 源码、协议说明、测试脚本、输入数据、实际日志、CSV/图、故障定位记录、简短演示和项目 README。当前均待完成。

## 5. FreeRTOS：官方 Linux/POSIX 示例

使用官方仓库中的 `FreeRTOS/Demo/Posix_GCC`，先学习内核最小示例。该移植让 FreeRTOS 应用运行在 Linux/POSIX 上；阅读资料时注意它与 FreeRTOS-Plus-POSIX 库的用途不同。

学习顺序：

1. 记录仓库版本、GCC/Make 版本与实际构建步骤，跑通最小示例。
2. 阅读任务、队列、软件定时器和示例选择配置。
3. 建立采集任务，由函数生成虚拟传感器数据。
4. 用队列将数据交给处理任务。
5. 用日志任务输出结果，处理队列满、超时和停止命令。
6. 为共享参数选择明确的同步方法，比较队列、互斥与任务通知。
7. 观察运行和阻塞逻辑，避免忙等待。
8. 将项目 1 的业务模块与传输接口分开，逐步接入任务结构。

验收重点是能解释并复现任务与同步行为。PC 移植受宿主 Linux 调度影响，不具备真实硬实时行为；STM32 中断延迟、DMA 吞吐、真实控制周期、芯片优先级和资源占用留待实板验证。

## 6. 项目 2：电机速度控制与双轮底盘软件仿真

**优先级：第二必做项目。** 无需电机、编码器或驱动板，控制器与被控对象分别封装。

### 6.1 单电机模型与控制器

- 用简化模型产生虚拟电机速度；控制器用 C 实现，Python 读取 CSV 并绘图。
- 从 P 或 PI 开始，再按需要理解 PID；加入输出限幅与明确的防积分饱和方法。
- 先固定采样时间和模型参数，再比较目标改变、负载扰动与参数变化。
- 每一步按“设定目标 → 计算控制量 → 更新模型 → 记录结果”执行。

原路线的一阶离散教学模型保留为：

`a = exp(−dt / τ)`

`ω[k+1] = a · ω[k] + (1 − a) · (K · u[k] − d[k])`

约定：`dt`、`τ` 以秒计，且 `dt > 0`、`τ > 0`；`u` 为归一化控制输入，需明确其上下限；`K` 的单位与速度单位匹配；`d` 是等效速度扰动，与 `ω` 使用相同速度单位。参数、初始值和扰动触发时刻写入记录。

这是教学模型，不表示已经测得真实电机参数，也不包含完整动力学。使用明确的模拟时间步推进；程序在电脑上运行的快慢不能用于证明 MCU 实时控制能力。

### 6.2 双轮二维仿真

- 左、右轮各有一个模型与控制器，复用协议、状态机和日志。
- 约定机器人向前为正、逆时针转动为正；轮距 `L > 0`，单位为米。
- 对线速度 `v`（m/s）和车体角速度 `ω`（rad/s），左右目标轮缘线速度为：
  - `v_left = v − ω · L / 2`
  - `v_right = v + ω · L / 2`
- 如轮模型使用轮角速度，先用轮半径 `r > 0`（m）换算：`ω_left = v_left / r`、`ω_right = v_right / r`。车体角速度与轮角速度使用不同变量名。
- 根据模型实际轮速计算车体运动：`v_body = (v_right + v_left) / 2`、`ω_body = (v_right − v_left) / L`。
- 固定步长积分位置与航向：`x_next = x + v_body · cos(θ) · dt`、`y_next = y + v_body · sin(θ) · dt`、`θ_next = θ + ω_body · dt`。注明这是简单欧拉积分，明确角度单位与坐标系。
- 绘制直线、圆弧、原地旋转轨迹，再加入噪声、延迟和通信中断；每次先改变一个因素。
- 通信超时进入明确定义的停车状态，记录触发条件和恢复策略。

理想无滑移模型不能证明真实底盘定位精度。轮距、轮半径、滑移假设、积分方式与时间步都写入报告。

### 6.3 验收清单

- [ ] 开环与闭环对比曲线。
- [ ] 目标速度、模型速度、误差与控制输出随模拟时间变化的图。
- [ ] 至少 3 组设定值与参数的重复测试，保留原始数据。
- [ ] 负载扰动、饱和、反转、通信超时场景的记录与分析。
- [ ] 双轮轨迹图、误差定义和可复现的参数文件。
- [ ] 能解释控制周期、积分饱和、单位转换、轮速公式和模型限制。
- [ ] 所有输出清楚标为仿真数据；将来若有实测，再分别记录。

项目质量依据控制模块、测试与解释能力评价。当前尚无测量值、曲线或验收结果。

## 7. 项目 3：ROS 2 与 Gazebo 导航仿真

**优先级：进阶。** 先完成项目 1、项目 2，再按实际基础进入本阶段。

当前已核对的官方组合为 **Ubuntu 26.04 + ROS 2 Lyrical + Gazebo Jetty**。Lyrical 支持 Ubuntu 26.04 的 amd64/arm64；用户已报告的 x86_64 对应 amd64。Lyrical 为 LTS，支持至 2031 年 5 月。正式安装前仍应重新查阅官方页面。

本路线不在 Ubuntu 26.04 上强行套用 Ubuntu 24.04/Jazzy 的软件源。若后来有明确课程或插件必须使用 Jazzy，再单独评估匹配的 Ubuntu 24.04 环境与迁移成本。

学习与验收顺序：

1. 学节点、话题、参数和 launch，先运行并解释基础通信。
2. 将自己的双轮仿真轮速、状态或里程计接入 ROS 2，理解 TF、时间戳与坐标。
3. 用 RViz 查看数据，核对单位与坐标方向。
4. **届时核对 Nav2 对 Lyrical/Jetty 的支持与所需依赖。** 选择匹配的官方 Quickstart，实际跑通示例后再承诺导航阶段排期。
5. 先在已有地图中发送目标点，再逐步做建图与保存。
6. 增加任务序列、取消、超时、结果记录和恢复行为。
7. 在不同起终点与障碍条件下重复测试，保留成功与失败记录并分析原因。

`Twist` 或 `TwistStamped` 根据所用发行版、节点与参数配置统一；不混用不同教程的接口默认值。

项目 3 验收清单：

- [ ] 记录 Ubuntu、ROS 2、Gazebo、Nav2 及相关包的实际版本和安装来源。
- [ ] 留下可复现的启动、地图加载、目标发送和结束步骤。
- [ ] 解释消息接口、速度单位、坐标系、时间戳与 TF 关系。
- [ ] 重复运行指定点与任务序列，保留每次起终点、场景、参数与原始日志。
- [ ] 实际记录成功、失败、取消、超时和恢复；未执行的场景标为待完成。
- [ ] 给出实际演示与限制说明；性能、成功率和耗时仅在真实运行后填写。

若虚拟机三维图形能力不足，先验收二维仿真、ROS 2 发布与 RViz，Gazebo 和 Nav2 后移。

## 9. Wokwi 可选练习与后续硬件

Wokwi 可用于所支持的 STM32 Blue Pill 等模型。练 GPIO、UART、I²C/SPI 等具体外设前，先查当前板卡支持表。原文提到的 DMA、IWDG 和 ADC 支持限制属于当时的资料，使用前重新核对。

- [ ] 核对板卡、外设和功能支持情况。
- [ ] 核对示例框架：Arduino、STM32 HAL 与寄存器开发各有不同。
- [ ] 不支持的外设验证后移，继续练可移植的协议和业务逻辑。
- [ ] 将仿真器限制与自己代码或配置问题分别记录。

有硬件后，根据岗位与预算选择一款具备调试条件的 STM32 板，再逐步增加外设。

| PC 阶段能力 | 后续实板需补充的验证 |
| --- | --- |
| 协议解析、环形缓冲、错误处理 | 真实 UART、DMA、中断与缓冲交接 |
| 虚拟传感器接口 | I²C/SPI 采样、时序与实际故障 |
| FreeRTOS 任务和同步 | 芯片优先级、栈/堆、中断与实际调度 |
| 电机模型与控制器 | 编码器、PWM、驱动、电源、真实负载 |
| 机器人仿真与导航 | 标定、轮滑、传感器噪声、通信与实车表现 |

硬件岗位还需补电路阅读、仪器使用与故障定位。实板能力由后续操作与证据补齐。
